# SPHEREx 3D — four-epoch full-sky explorer

The `SPHEREx 3D` tab renders one sphere with four epoch states, a timeline, and a
GPU-instanced change-candidate layer. It is deliberately separate from the
validated `SPHEREx FIELD` tab.

## Scientific status

**The global layer is illustrative, not a measurement.** The repository contains
two real reprojected SPHEREx NEP observations under `data/spherex/derived/`
(`epoch-a`, `epoch-b`). It does not contain a four-epoch all-sky archive. The
four global epochs are deterministic prototype data generated by
`server/spherex/sky-tiles.js` so the interaction, streaming and timeline can be
built and tested end to end.

The real NEP products remain the validated detail layer in `SPHEREx FIELD`.
The 3D page says so in its HUD, its provenance card and its API metadata.

There is no difference, subtraction, variability statistic or motion
measurement route or control. The single-epoch views are shown side by side in
the source table only so a user can inspect the prototype; they do not establish
a detection. The `SPHEREx FIELD` gate (`quantitative_difference_enabled: false`)
is unchanged.

## What the server serves

| Route | Purpose |
| --- | --- |
| `GET /api/spherex/sky` | Index: epochs, coverage, HEALPix NEST levels, URL templates, source-layer pointer, performance hints |
| `GET /api/spherex/sky/sources` | GPU-instanced candidate measurements for all four epochs |
| `GET /api/spherex/sky/base/:epoch.png` | 512×256 equirectangular RGBA base, one per epoch |
| `GET /api/spherex/sky/tile/:epoch/:order/:ipix.png` | 128×128 RGBA HEALPix NEST tangent-plane patch |

Example epoch IDs are `epoch-1` … `epoch-4`. Tile orders are `1` (48 pixels)
through `4` (3,072 pixels). The index declares `scheme: "healpix-nest"`,
`ordering: "NEST"`, `baseOrder: 1`, `maxOrder: 4`.

### Raster conventions

Both rasters are PNG, north-up, and use alpha 0 for sky that the epoch does not
cover. A missing pixel is never filled with a zero measurement.

* Base: column 0 is RA 0, row 0 is Dec +90; the image is equirectangular.
* Tile: the centre is the HEALPix NEST pixel centre; east is the local +u axis
  and north is the local +v axis. The renderer reconstructs the same patch with
  `normalize(center + east*u*half + north*v*half)` and the same
  `tileHalfAngleRad(order)` as the server.

The client decodes the PNG into an `ImageBitmap` that is **pre-flipped during
decode** (`imageOrientation: "flipY"`), then uploads it with `texture.flipY =
false`. WebGL ignores `UNPACK_FLIP_Y_WEBGL` for `ImageBitmap` uploads; without
the explicit flip the whole sky would be vertically mirrored. This contract is
pinned by `client/src/lib/sky-tile-decode.test.js`.

### Cache and error semantics

Both raster routes send `Content-Type: image/png`,
`Cache-Control: public, max-age=86400, stale-while-revalidate=604800`,
`ETag`, `X-Novochar-Sky-Mode: illustrative` and
`X-Novochar-Sky-Cached` (in-process cache hit/miss). A matching
`If-None-Match` returns `304` with no body. Invalid epoch/order/pixel requests
return a JSON error, never a blank image.

The PNG cache is in-memory and per process. Vercel's `/tmp` is not used as
durable storage.

## Client architecture

| File | Responsibility |
| --- | --- |
| `client/src/components/SpherexSky3D.jsx` | Tab UI, timeline, epoch stops, candidate table, performance HUD, FIELD bridge, error/WebGL2 states |
| `client/src/lib/sky3d-engine.js` | Three.js scene, custom camera controls, base sphere, HEALPix tile meshes, instanced candidate shader, adaptive DPR/detail, prefetch, disposal |
| `client/src/lib/sky-tile-loader.js` | Deduplicating priority queue, worker pool, abort/cancel, main-thread fallback, stats |
| `client/src/lib/sky-tile-worker.js` | Fetch + decode off the main thread |
| `client/src/lib/sky-tile-decode.js` | North-up `ImageBitmap` decode (the flip contract) |
| `client/src/lib/sky-tiles.js` | URL helpers, view-dependent LOD, nearest HEALPix pixels, LRU texture cache, device quality profile |
| `shared/astro/healpix-nest.js` | One shared NEST implementation for server and client (pixel centres, children, parents, angular size) |

The engine renders on demand; it is not a free-running animation loop. The
timeline defaults to paused. The base texture is fetched first, then a central
island of order-2 tiles, then higher orders as the user zooms. Stale requests
are cancelled when the view or epoch changes; a small prefetch of the next
epoch's base and twelve base-order tiles runs only when the browser is idle and
the device is not in the low tier.

Quality profiles:

* **standard**: up to order 4, 192 textures, 2 workers, DPR cap 2, prefetch.
* **low** (coarse pointer, small viewport, `Save-Data`, ≤4 GB device memory or
  ≤4 logical cores): up to order 3, 128 textures, 1 worker, DPR cap 1.25, no
  prefetch.

Frame time drives a bounded DPR reduction and, on sustained slowness, a lower
detail order. The page also honours `prefers-reduced-motion` by not autoplaying
the timeline.

## Four epochs and coverage

The four epochs are four observations of **one** sky, not four separate
universes. The UI shows the epoch identity and the sampled coverage fraction;
the gaps are actual alpha-0 regions in the tiles and base.

The illustrative model exposes representative gaps:

* epoch 1: full coverage;
* epoch 2: gap around RA 194–238°, Dec −1–23°;
* epoch 3: no coverage below Dec −66°;
* epoch 4: gap around RA 16–55°.

These numbers are prototype coverage semantics, not archive coverage. A future
archive ingestion replaces them with measured coverage and the same client
contract.

## Real archive ingestion path

The tile contract is production-shaped. To replace the prototype with real
SPHEREx data:

1. Ingest the chosen archive products (IRSA / SPHEREx quick-release or a
   contributed level-2/3 product) with their WCS, mask, units and provenance.
2. Validate the WCS, photometric calibration and mask; reject products that do
   not pass the same alignment gate used by `SPHEREx FIELD`.
3. Reproject each epoch onto the agreed sky frame and generate HEALPix NEST
   tiles at orders 1–4 plus the equirectangular base. Keep row 0 north and
   alpha 0 for no-coverage.
4. Store the tiles as immutable, content-addressed products with source
   SHA-256s and generation metadata — not in `/tmp`.
5. Update `skyIndex()` to declare `mode: "archive"`, real epoch dates, measured
   coverage and archive provenance. Keep the same route names and raster
   conventions so the client does not change.
6. Add acceptance checks that compare sampled tile pixels with the source
   measurements and that fail loudly if a tile is filled-in, mirrored or
   mis-registered.
7. Keep the real NEP detail layer in `SPHEREx FIELD`; do not replace it with the
   global mosaic.

The current in-repo implementation intentionally fails step 1 (the data does not
exist in the repo), so it must remain labelled `illustrative` until a real bundle
lands.

## Deployment

The 3D routes do **not** need Python, the sidecar, a network fetch or `/tmp`.
They use the same Node server as the rest of the API; Vercel rewrites
`/api/:path*` to the function in `api/index.js`. The real NEP bundle remains
committed under `data/spherex/derived/` and included by `vercel.json` for the
FIELD routes. Raster responses are CDN-cacheable, so a warm deployment does not
regenerate the same base or tile for every visitor.

## Verification

```bash
npm test                         # unit + contract tests
npm run build                    # bundle check + precompute + client build
npm run check:spherex3d          # browser acceptance (needs built client + Chromium)
npm run verify:deployment -- https://your-deployment.example
```

`check:spherex3d` boots the production server and checks the index/source/raster
contracts, WebGL2 rendering, non-blank pixels, epoch switching, source focus,
marker visibility, play/pause, reset, the absence of difference controls, the
FIELD bridge, the mobile low-quality profile and the no-WebGL fallback.
